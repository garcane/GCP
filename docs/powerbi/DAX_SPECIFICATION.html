DAX and Power BI specification

Retail Analytics, Forecasting & Customer Intelligence (Olist data). Step 1 of 3: this specification → mock-up → powerbi/RetailAnalytics.pbip.

Overview

This page specifies a four-page Power BI report over the project's star schema: the semantic model (tables, relationships, DAX measures) and the report (pages and visuals). It is generated from src/powerbi/model_spec.py, which also generates the mock-up and the Power BI project, so the three cannot disagree. Every measure lists the SQL it mirrors and the value it should return, so the numbers in Power BI can be checked against the warehouse.

Status. The DAX has not been executed here: Power BI Desktop is not available in the build environment. The values below are computed from the warehouse by SQL, and the first-open checklist is how to confirm that each DAX measure returns the same number.

Set-up in Power BI Desktop

  1. Install Power BI Desktop (Windows, free). Open powerbi/RetailAnalytics.pbip.
  2. When prompted (or via Transform data → Manage parameters), set the text parameter DataFolder to the full path of powerbi/data, with no trailing backslash.
  3. Refresh. Every table should load; row counts match the table above.
  4. Work through the first-open checklist.

Relationships

All are many-to-one with a single filter direction (from the one side to the many side). Items, payments and reviews reach dates, customers and states through their order, so there is exactly one filter path to each table and no ambiguity. The order table keeps one active relationship to the date table (purchase date) and four inactive ones for the other milestones; a measure opts in with USERELATIONSHIP.

Notes and limitations

  • Not executed here. Power BI Desktop was not available when this was generated, so no DAX measure has been run and the .pbip has not been opened. Report files were validated against Microsoft's published JSON schemas; the model files follow the TMDL documentation. Expect that a first open may need small fixes.
  • Pooled versus averaged lift. The Lift measure pools the selected orders, so with all six months selected it shows 2.44x; the 2.8x quoted in the model card is the average of the six monthly lifts (March 2018's high late rate weighs on a pooled figure).
  • Payments do not tie to revenue. Payment Value (all payments) is analysed on its own and differs from net item revenue, by design (DD-04).
  • Category table. The category bar chart lists all 74 categories sorted by revenue (no Top-N filter); per-category average review score is not included because reviews belong to orders, not items.
  • Out-of-time scores. The risk page shows scores for 2018-03 to 2018-08 only; probabilities are not reliable in level, so the page is built around rank (flag the riskiest X%).
  • Forecast methods are the project's baselines; on 85 weeks the ranking of the complex methods is not reliable (see the model card).
  • No credentials. The project reads local files only; DataFolder is a local path set by the user.
